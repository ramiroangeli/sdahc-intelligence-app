# Listings platform: architecture summary (as built, November 2026)

This describes what is deployed now. Do not assume an older System Atlas matches it.

## Two repositories, one pipeline
| Part | Repository | Hosting |
|---|---|---|
| Public website (Astro, static) | `ramiroangeli/sdahc-website` | Vercel, https://sdahomechoices.com.au |
| Listings Manager (internal app, vanilla JS plus 12 serverless functions under `api/listings`) | `ramiroangeli/sdahc-intelligence-app` | Vercel, https://app.sdahomechoices.com.au |

Notion is the CRM and is only read. Drafts, history, publication jobs and the audit log are in the operational Postgres (Supabase, schema `listings`, access only for the `listings_app` role, RLS on). Photographs: private staging store, then a public Vercel Blob store at publication.

## Data flow
1. Staff create a draft from a CRM property (Notion read-only). The draft holds only public wording, address, pricing, photographs and optional details. CRM price, income and yield are never copied.
2. Preview is built from the draft with the website's own rules (the app vendors the website's listing core, `api/_lib/vendor/listings-core.mjs`, generated by `scripts/vendor-listings-core.mjs`).
3. A Publisher starts publication. The app freezes a signed (HMAC) request from the stored draft, copies approved images to the public store, and dispatches a GitHub Actions workflow through the GitHub App "SDAHC Listings Publisher".
4. The workflow (`scripts/listings-publish-job.mjs` in the website repo) fetches the request, rebuilds the snapshot with the website engine, runs parity checks, tests, build and privacy scan, opens a one-file pull request, waits for the required check, merges, waits for deployment and proves the live page. It reports back by signed callbacks.
5. Production serves the merged snapshot. Withdrawal is a permanent tombstone.

## Controls that matter
- Roles (`LISTINGS_STAFF_JSON`): Viewer, Editor (`listings.edit`), Publisher (`listings.publish`), administrator. Every route checks on the server.
- Two independent safety layers: the app's validation and the website engine's `checkPublicSafety`. Public text may not carry addresses with numbers, dollar amounts or income and yield wording, email, phone, private links, or the CRM price or yield.
- Commercial block (lease, occupancy, income, yield): stored privately, published only while a Publisher approval record matches its exact values. The record is written by the server from the stored values and the session (`verification.investment_disclosure`); browsers cannot supply it; editing a value removes it. Victorian listings never publish income or yield (conservative rule, pending legal review). Sold listings never carry the block.
- Descriptions: free text can be saved and previewed, but text with figures cannot be published (app refuses the request with a specific reason; the website engine also refuses).
- Approver identity and notes stay in the private draft record and audit log. The public request, snapshot and pull request name nobody.
- Branch rules: squash merge only, required checks (`site-checks` for the website, `test` for the app), no direct pushes.

## Limits and constraints
- Vercel plan allows 12 functions; the app uses exactly 12 under `api/listings`. A new function needs a plan change or merging routes.
- The vendored core must be re-generated when the website listing core changes (`node scripts/vendor-listings-core.mjs --from <website checkout>`; it records the source commit).
- No schema change was needed for optional fields or approvals (existing `verification` jsonb and `verify` history action).
